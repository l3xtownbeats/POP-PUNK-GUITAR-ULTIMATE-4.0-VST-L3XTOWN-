## 3. Подтверждённая техническая база и риски

Последний углублённый аудит SamplePool/SamplerEngine подтвердил:
- загрузка SFZ строит candidate snapshot и публикует его атомарно после проверки generation token;
- старые snapshots и streaming services удерживаются до уничтожения SamplePool для защиты активных raw pointers;
- текущие ограничения: до 128 snapshots и до 8 streaming library roots на экземпляр;
- SamplerEngine содержит 64 заранее выделенных voice slots;
- cache miss не должен блокировать audio thread; voice удерживает cursor до получения страницы;
- streaming worker дренирует очередь при штатной остановке;
- после исключения worker автоматически не восстанавливается.

Открытые инженерные риски:
1. безопасное освобождение старых snapshots без use-after-free;
2. совокупная память/потоки при нескольких streaming roots;
3. политика восстановления после падения streaming worker;
4. стресс 64 voices при cache pressure, queue overflow и loop prefetch;
5. cancellation/lifetime гонки при загрузке и уничтожении processor;
6. полная Windows Release + CTest + pluginval проверка после изменений.

Нельзя удалять старые snapshots простым сбросом unique_ptr, пока не доказано quiescence всех audio readers.

## 4. Архитектура семейства Guitar / Bass

Принято: один общий низкоуровневый PPGU Audio Engine и два самостоятельных продукта — Guitar Edition и Bass Edition. Общими могут стать streaming, WAV/SFZ reader, cache, queues, state/preset infrastructure, MIDI primitives, FX infrastructure и QA. Guitar/Bass артикуляции, SoundBank, presets, product identity и UI-профили остаются раздельными. Это архитектурное решение, не готовая реализация.

## 2026-11-12 — C1083 / generated BinaryData.h regression fix

**Статус:** SOURCE FIX COMMITTED; WINDOWS BUILD PENDING.  
Source commit: `0ef0ebe934350d57779328a5e0979f1134ae85f2` (parent: `e21980eee5289b00db371b3c2a907a5d0016b19a`).

В `CMakeLists.txt` добавлена отдельная JUCE binary-data цель `PPGUTestData` до создания зависимого integration-test target. Цель использует маленький нейтральный fixture `tests/assets/ppgu_test_data.txt`, namespace `PPGUTestData` и линкуется непосредственно к `ppgu_processor_pattern_tests`. Это обеспечивает generated include directory и `JUCE_TARGET_HAS_BINARY_DATA` для test target в чистом build tree.

**Важное уточнение JUCE API:** в закреплённой проектом JUCE 7.0.12 сигнатуре используется аргумент `NAMESPACE`, а не `HEADER_NAMESPACE`; сгенерированный заголовок по умолчанию называется `BinaryData.h` и попадает в include directory target. Поэтому путь `PPGUTestData/BinaryData.h` из чернового примера REV 13 не используется: JUCE добавляет generated header через `JuceHeader.h` при наличии `JUCE_TARGET_HAS_BINARY_DATA`. Основание: JUCE CMake API и реализация `juce_add_binary_data`.

GitHub Actions run #827 / ID `43113647167` создан на source commit `0ef0ebe934350d57779328a5e0979f1134ae85f2`; на момент записи состояние `queued`. Локальная Windows/MSVC Release-сборка в этой среде не выполнялась. Следовательно, исправление пока **не объявляется BUILT или TESTED**. Следующие гейты: полный build всех targets, CTest, locate VST3, pluginval strictness 5 и packaging.

Отдельное расхождение REV 13 для последующего согласования: текущий root CMake всё ещё закрепляет JUCE 7.0.12 и minimum CMake 3.22; REV 13 §13.2 требует JUCE 8 и CMake >=3.24. Версии не менялись в рамках изолированного C1083 fix, чтобы не смешивать причины сборочных регрессий.

## 2026-11-12 — PATTERN guitar / tone / articulation workflow clarification

Approved user clarification: PATTERN workflow is separated into three independent choices:
1. Guitar/instrument source (electric/acoustic and available recorded instrument profile).
2. Tone preset (e.g. Pop Punk Lead, Punk Rock Rhythm, Clean/Crunch/Drive, Flanger or Tremolo tone); tone and FX do not replace performance changes.
3. Performance articulation/variation (open strum, lead/octave hook, palm mute/tight, muted bridge, sustain/ambient, tremolo picking, arpeggio, stop-start/syncopated, downstroke, alternate down-up), limited to articulations backed by real recordings.

User's primary functionality references: Native Instruments Session Guitarist Electric Sunburst Deluxe and Vintage; Neon is an additional reference. Tom DeLonge's Blink-182 / Angels & Airwaves performance vocabulary is an inspiration target for original patterns (driving downstrokes, power chords, octave hooks, palm-muted verses, open chorus lift and sustained/ambient lead textures), not permission to copy recordings, riffs or proprietary presets.

PATTERN variations must be switchable during playback with host sync and clean transitions. Optional compatible layering may be an advanced feature; it must not be the default behavior and must respect CPU/polyphony limits. Tone effects (flanger, tremolo effect, delay, reverb, distortion) are distinct from playing techniques (tremolo picking, palm mute, strumming, etc.). Every displayed articulation requires a matching recorded performance/one-shot/loop map and runtime verification; unavailable articulations must be marked unavailable rather than simulated with synthetic guitar.

Specification updated in `docs/MASTER_PRODUCT_SPEC_4_0_RU.md` §15.7. This is an approved product requirement, not evidence that the runtime UI, sample maps or playback engine already implement it.

## 9. SOUND FORGE — ресурсный контракт (2026-11-12)

Пользователь утвердил приоритет: расширять и улучшать гитарную библиотеку без заметного роста потребления CPU, RAM, диска и энергии компьютера/ноутбука. SOUND FORGE проектируется как offline/non-realtime подготовка материалов, а не как тяжёлая обработка внутри игрового движка.

### 9.1 Разделение runtime и подготовки
- VST3 runtime отвечает за воспроизведение уже подготовленных инструментов; сканирование каталогов, конвертация, ресемплинг, анализ, fingerprinting, хэширование и пакетная обработка запрещены в audio callback.
- SOUND FORGE выполняет импорт/конвертацию/улучшение вне DAW realtime path: предпочтительно отдельный companion/curator process или явный пользовательский offline job. Пока отдельный production target не реализован, не заявлять наличие готового SOUND FORGE.
- Не запускать фоновые анализаторы при открытии плагина без явного запроса пользователя. Не держать постоянно активный worker ради неиспользуемой библиотеки.
- Исходники сохраняются неизменными; все производные файлы версионируются и могут быть пересозданы.

### 9.2 Бюджет игрового движка
- Сохранять текущую bounded streaming архитектуру: 64 заранее выделенных voice slots, максимум 8 streaming roots, 256 cache slots на root, 4096 frames/page. При stereo float это около 8 MiB cache/root и до 64 MiB суммарно для восьми roots; это верхняя граница только page cache, не полная RAM плагина.
- Не увеличивать эти лимиты без профилирования на целевых Windows 10 x64 системах и сравнительных измерений.
- Не декодировать целые библиотеки в RAM; использовать существующий metadata index и bounded page streaming. Не создавать thread-per-sample/voice/preset.
- Не добавлять обязательный neural/AI denoising, oversampling или постоянные спектральные анализаторы в realtime path.
- Конвертировать в заранее выбранный playback format один раз offline; не ресемплировать файлы каждый раз при старте ноты или смене пресета.
- Не делать лишних копий буферов. Любые новые кэши должны иметь фиксированный лимит, явную политику eviction и измеряемый worst-case.

### 9.3 Бюджет SOUND FORGE offline
- По умолчанию один активный job и ограниченная очередь; concurrency configurable, default 1. Pause/cancel/resume обязательны для длительных задач.
- Обработка блоками/чанками, а не загрузка всех исходников в память. Память ограничивается размером рабочих буферов и небольшим числом одновременно открытых файлов.
- При работе от батареи — режим LOW POWER: один worker, отсутствие параллельных fingerprint/preview задач, возможность приостановки. Не использовать GPU как обязательную зависимость.
- Предпрослушивание использует тот же bounded playback path; не запускать несколько скрытых preview streams.
- Disk quota и free-space preflight обязательны; временные файлы очищаются при отмене/ошибке, оригиналы не перезаписываются.

### 9.4 Качество и измерения
- Улучшение не должно означать безусловное шумоподавление/нормализацию: сохранять атаку, динамику, transient, естественный шум инструмента и фазу; каждое преобразование сравнивается с оригиналом A/B.
- Lossless conversion по умолчанию. Lossy source не повышается фиктивно до lossless quality; sample-rate conversion не объявляется улучшением исходного качества.
- Для каждого этапа фиксировать wall time, peak working-set/RAM, CPU time/load, bytes read/written, число worker threads и итоговый размер. Сравнивать с baseline текущего HEAD на одном и том же компьютере/настройках.
- Release gate: никаких заявлений «потребляет столько же» или «не влияет на батарею» без повторяемых измерений. Целевой принцип — отсутствие дополнительной постоянной нагрузки в idle и отсутствие роста realtime CPU/RAM относительно текущего sampler baseline сверх измеренного допуска.

### 9.5 Статус
RESOURCE CONTRACT APPROVED AS DESIGN. Это архитектурное решение, не реализованный SOUND FORGE, не измеренный benchmark и не подтверждение неизменного энергопотребления. Следующий шаг — baseline profiling существующего sampler (idle, 1/16/32/64 voices, streaming/cache pressure, preset load) и затем реализация offline processor с тестами ограничений памяти/потоков.

## B. MELODY + PATTERN — основной незакрытый функциональный блок

### B1. Утверждённое поведение
- MELODY — полноценная обычная MIDI-игра: одна клавиша звучит как отдельная нота; несколько одновременно нажатых клавиш звучат как ноты/аккорд. Обычные MIDI-ноты не должны требовать наличия PATTERN.
- PATTERN — дополнительный способ исполнения внутри MELODY, а не замена обычной игры и не арпеджиатор по умолчанию.
- В Piano Roll основная нота/аккорд задаёт гармонию, а отдельное событие в дополнительной/третьей графе PATTERN служит управляющим триггером выбранного ритмического рисунка.
- Триггер не должен звучать как гитарная нота и не должен трактоваться как ступень аккорда.
- Если PATTERN-триггера нет, MELODY работает обычно. Если триггер есть, рисунок исполняется на текущей гармонии.
- При смене аккорда активный рисунок подхватывает новую гармонию без сброса ритмической фазы.
- Смена/отсутствие триггера не должна ломать MIDI note-on/off, полифонию, release, sustain и обычное исполнение.
- Требуются чёткие правила trigger note-on/note-off, latch/hold, retrigger, переключения рисунка, остановки транспорта, seek/loop, panic, смены пресета и одновременных триггеров.

### B2. Текущая рабочая ветка — не считать уже принятой в main
- Ветка `work/ppgu-completion-integrated-2026-11-13` содержит отдельный `PatternTriggerMap`, контрактный тест и интеграцию триггеров C0–C1 (MIDI 12–24) в processor. В этом mapping 13 клавиш назначены на 13 слотов.
- В просмотренном исходнике триггерные события исключаются из обычного Melody note playback; удерживаемые ноты отдельно используются как гармонический снимок для PATTERN; состояние триггера управляет выбором слота.
- Это текущая реализационная схема ветки, а не окончательная приёмка поведения. Нужно подтвердить MIDI octave naming и удобство диапазона в FL Studio 20, проверить соответствие фактической раскладке Piano Roll и согласовать UX-индикацию.

## E. Streaming Sample Engine / Page Cache

Принято гибридное решение: bounded Streaming Sample Engine + Page Cache. Не заменять его загрузкой всех библиотек в RAM.

- Prefetch небольших стартовых участков; остальное читать асинхронно worker-потоками.
- Audio thread делает только неблокирующее чтение готовых страниц; cache miss не ждёт диск.
- Кэш ограничен и имеет понятную eviction/pinning политику; параметры памяти настраиваются под доступную RAM без потери стабильности.
- Проверить lifetime snapshots, page handles, readers, voices, bank reload/unload и destruction processor; исключить use-after-free, data race и stale pointer.
- Проверить queue full/overflow, duplicate requests, worker stop/drain, worker exception/recovery, диск с задержками, отсутствующий/повреждённый файл, loop prefetch и underrun counters.
- Проверить одновременно 64 voices под cache pressure и максимальное число streaming roots; зафиксировать peak RAM и поведение при лимите.
- Проверить, что worker не перезапускается бесконечно и что failure state виден/восстанавливается контролируемо.
- Добавить stress/soak tests, ThreadSanitizer/AddressSanitizer где возможно, повторную загрузку банков во время звучания и закрытие processor во время длительной загрузки.
- Текущая базовая конфигурация из предыдущего аудита: 64 заранее выделенных voice slots; до 8 streaming roots; 256 cache slots/root; 4096 frames/page; ориентировочно до 8 MiB/page cache на root и до 64 MiB на восемь roots (не полный RAM footprint).
- Эти числа — текущие ограничения, не доказательство корректной работы на всех конфигурациях. Не увеличивать без benchmark.

## 9. Полный технический паспорт проекта

**Назначение раздела:** единая техническая карта PPGU — из чего состоит продукт, на каких технологиях работает, как проходит MIDI/audio signal, как устроены sampler, streaming, DSP, PATTERN/MELODY, интерфейс, пресеты, SoundBank, сборка и проверка. Здесь фиксируется подтверждённая реализация отдельно от целевой архитектуры.

### 9.1. Платформа, язык и сборочная система
- Продукт: виртуальный гитарный инструмент VST3, Windows x64; целевой хост — FL Studio 20.
- Основной язык: C++20. GUI, plugin processor/editor и DSP-инфраструктура построены на JUCE; текущая закреплённая версия — JUCE 7.0.12.
- Система сборки: CMake; целевой компилятор — MSVC / Visual Studio 2022 x64.
- Текущие профили аудио-проверки в документации: 48 kHz / 64 samples. Это тестовый профиль, а не единственно допустимый режим работы.
- Целевой формат поставки — VST3 bundle с необходимыми легально распространяемыми SOUNDBANK, PRESETS, SKINS, Resources и Assets.
- Сборка текущего HEAD, CTest, pluginval, установка и работа в FL Studio 20 должны подтверждаться отдельно. Наличие CMake/JUCE исходников само по себе не является доказательством готового бинарного продукта.

### 9.2. Общая структура аудиотракта
Логическая цепочка инструмента:
1. MIDI/host events поступают в plugin processor.
2. Processor передаёт события выбранному инструментальному режиму и voice/scheduler подсистемам.
3. MELODY запускает ноты непосредственно по MIDI-клавиатуре.
4. PATTERN использует chord-oriented workflow, транспорт и scheduler-компоненты для формирования ритмических событий.
5. Sampler/voice layer выбирает SFZ region с учётом доступных key/velocity/channel/RR mapping данных.
6. Голоса читают аудиостраницы через streaming reader; cache miss не должен заставлять audio thread ждать диск.
7. Суммированный сигнал проходит через доступные DSP-узлы и формирует выходные аудиоканалы плагина.

Это схема архитектурного потока. Полная сквозная runtime-приёмка PATTERN → sampler → FX → host на текущем HEAD ещё не подтверждена.

### 9.3. MELODY и PATTERN
- MELODY — хроматическая MIDI-игра: отдельная нота на клавишу, риффы, октавы, хуки и lead-партии.
- PATTERN — аккордовый ритм-режим для downstrokes, palm-muted куплетов, открытых припевов, offbeat и арпеджированных рисунков.
- В проекте присутствуют транспортные и scheduler-компоненты PATTERN. Их наличие не приравнивается к завершённой работе всех сценариев.
- Для PATTERN требуется отдельная end-to-end проверка: выбор/смена аккорда, секция/фрагмент песни (например verse/chorus/bridge), выбор рисунка и ритмики, tempo/transport sync, MIDI timing, артикуляция, остановка/перезапуск, смена пресета и сохранение состояния.
- Изменения PATTERN не должны ломать прямой MELODY workflow или общий audio callback.

### 9.4. Sampler и формат сэмплов
Подтверждённая базовая реализация — SFZ/WAV sample playback path:
- SFZ parser формирует region mapping; отдельные механизмы учитывают key range, velocity, MIDI channel и round-robin.
- WAV metadata index выполняет metadata-only scan: frames, sample rate, channels, bit depth, floating-point flag, file size и modification time. Сам scan не декодирует весь аудиофайл.
- SamplePool связывает SFZ parsing, metadata index, streaming service и RegionView; активный snapshot публикуется атомарно после подготовки.
- SamplePool ограничен 128 snapshots и 8 уникальными streaming library roots на экземпляр.
- SamplerEngine содержит 64 заранее выделенных voice slots; музыкальная целевая полифония по профилю проекта — 32, но нагрузочная приёмка 64 voices остаётся отдельной задачей.
- Полнота стандарта SFZ не заявляется. WAV — подтверждённый путь; прямой универсальный импорт FLAC/OGG/AIFF/SF2 не подтверждён. Наличие fallback для OGG reference к одноимённому WAV не означает прямое OGG streaming.

### 9.5. Streaming и page cache
Подтверждённые исходные компоненты:
- Source/Sampler/SampleMetadataIndex.{h,cpp} — индекс WAV metadata.
- Source/Sampler/SampleStreamingService.{h,cpp} — bounded SPSC request queue, worker thread, page decoding и статистика запросов/cache hit/miss/decode errors/cache full.
- Source/Sampler/PageCacheSlots.{h,cpp} — фиксированные cache slots, атомарный pin/release и eviction только незакреплённых готовых страниц.
- Source/Sampler/StreamingVoiceReader.{h,cpp} — page-backed reads, prefetch соседних страниц и Hermite interpolation через границы страниц.
- Source/Sampler/SamplePool.{h,cpp} — подготовка SFZ snapshot и публикация RegionView для аудиопотока.

Текущие параметры/ограничения, подтверждённые аудитом:
- 4096 frames на страницу; до 2 каналов; 256 cache slots.
- Лимит cache — 256 MiB на один streaming service/root; до 8 roots означает потенциально до 64 MiB page buffers при текущем размере слота/страницы по расчёту аудита.
- Один streaming service использует один SPSC producer/consumer contract; подключать несколько audio producers без пересмотра очереди нельзя.
- Worker idle loop использует sleep_for(1ms); оптимизация wake-up должна сохранять корректный shutdown.
- Cache page lease/pin защищает чтение от eviction во время использования.
- При cache miss audio thread не ждёт disk/worker; недостающий участок может быть пропущен/заглушён согласно underrun policy, запрос ограниченно ставится в очередь.
- Старые snapshots и streaming services удерживаются до уничтожения SamplePool, чтобы не освободить память под активными raw pointers. Это защитная, но потенциально растущая по памяти стратегия.
- Нельзя удалять старые snapshots через простой reset unique_ptr. До reclamation нужен доказанный reader-quiescence/epoch/refcount handoff.
- Worker shutdown требует producer quiescence; автоматическое восстановление worker после исключения не подтверждено.

### 9.6. Realtime safety — обязательный контракт
В audio callback/processBlock запрещены:
- файловый и сетевой I/O;
- WAV decode и SFZ parsing;
- ожидание mutex/condition variable/worker;
- неограниченные операции и ожидание свободного cache slot;
- GUI операции;
- непредсказуемые выделения/освобождения памяти после начала воспроизведения.

Разрешённый принцип: заранее выделенные структуры, bounded queues, атомарная публикация готовых данных, неблокирующий lookup и чтение уже закреплённых страниц. Любое изменение ownership, voice stealing, panic/release, snapshot reclamation или queue topology требует regression/stress tests. Приоритеты проекта: безопасность → realtime → звук → ресурсы → UX.

### 9.7. Voice management и MIDI
- 64 заранее выделенных sampler voice slots.
- MIDI mapping включает note, velocity и channel; SFZ region selection имеет отдельные механизмы key/velocity/channel и round-robin.
- Voice lifecycle включает start/release/steal/panic и удержание page leases; все эти пути должны быть проверены на отсутствие утечек и use-after-free.
- 64-voice stress под cache pressure, queue overflow, одновременными note hits и длительным sustain остаётся незакрытым QA пунктом.
- UI MIDI keyboard и host MIDI должны быть проверены совместно; отображение клавиатуры не заменяет тест входящих MIDI events из DAW.

### 9.8. DSP и эффекты
В проекте заявлены/присутствуют DSP-компоненты и контролы:
- Compressor;
- EQ;
- Distortion;
- Chorus;
- Delay;
- Reverb;
- Cabinet.

Это список DSP областей проекта, а не подтверждение законченной звуковой приёмки каждой цепочки. Требуется проверить параметры, bypass, reset/defaults, автоматизацию host, корректность stereo/mono routing, отсутствие denormal/noise/NaN, поведение при смене пресета и нагрузку на CPU. Точная топология, oversampling, фильтры, коэффициенты и latency должны фиксироваться после чтения актуального исходного кода соответствующих DSP классов; предположения не записывать как факты.

### 2. Канонический порядок preset browser

Основная навигационная цепочка:

**GENRE → ARTIST/BAND → SONG/SECTION → STYLE → PATTERN**

Уровни имеют самостоятельный смысл и не должны сливаться в один плоский список:
1. GENRE — музыкальная категория/направление.
2. ARTIST/BAND — artist-inspired группа стилевых ориентиров; это метаданные характера, а не копирование чужих записей/пресетов.
3. SONG/SECTION — выбор музыкального контекста и части композиции.
4. SECTION — Intro, Verse, Pre-Chorus, Chorus, Bridge, Outro.
5. STYLE — характер исполнения/ритмическая манера внутри выбранного контекста.
6. PATTERN — конкретный ритмический рисунок/вариант исполнения.

Названия групп и композиций служат только навигационными/стилевыми метками. Нельзя включать защищённые мастер-записи, риффы, коммерческие пресеты или выдавать artist-inspired материал за официальный материал артиста.

### 3. Обязательные browser controls и их поведение

В полном браузере должны быть предусмотрены и связаны с реальными операциями:
- BROWSER — открыть/закрыть область браузера;
- FAVORITES — быстрый доступ к избранному;
- CATEGORIES — выбор категории/режима/раздела;
- SEARCH — поиск по доступным метаданным;
- FILTER — фильтрация с сохранением контекста;
- SORT — сортировка;
- PREV / NEXT — предыдущий/следующий результат в текущем отфильтрованном наборе, а не переход к случайному или глобально соседнему элементу;
- FAVORITE — добавить/убрать текущий элемент из избранного;
- PRESET NAME и CATEGORY — ясно показывать выбранный объект и его тип;
- PREVIEW — предварительно прослушать/проверить выбор;
- SELECT — выбрать/загрузить подтверждённый элемент.

Существующие категории MELODY / PATTERN сохраняются. Не смешивать заводские пресеты, пользовательские пресеты, банки, performance styles и отдельные Pattern entries в одну сущность: у каждого типа должны быть ясные метаданные и допустимые операции.

### 4. Preview / Apply / Cancel — транзакционная семантика

- PREVIEW не меняет активный preset, активный проект, сохранённое состояние DAW или текущие рабочие параметры. Это временное audition/предпросмотр.
- APPLY подтверждает выбор и только тогда применяет/сохраняет его в соответствующем контексте.
- CANCEL отменяет незавершённый выбор и возвращает исходное состояние до начала транзакции.
- Повторный Preview, переключение между вариантами и закрытие окна не должны оставлять частично применённые значения.
- Для Theme Gallery действует та же безопасная модель: Preview не меняет постоянную тему; Apply применяет; Cancel закрывает/откатывает незавершённый выбор. Тема не меняет звук.
- Preview pattern должен использовать безопасный audition path и не портить текущую позицию/состояние проекта; остановка preview обязана корректно завершать временные голоса/события.

### 5. PATTERN: секции, слоты и редактирование рисунка

- Выбор композиционного контекста проходит через SONG/SECTION; поддерживаемые секции: Intro, Verse, Pre-Chorus, Chorus, Bridge, Outro.
- Для каждой секции предусмотрено **8 Pattern Slots**. Слоты — отдельные варианты рисунка внутри секции; они не заменяют саму секцию и не являются восемью автоматическими factory presets.
- После выбора SECTION пользователь выбирает STYLE, затем конкретный PATTERN/Pattern Slot.
- Preview — неразрушающий audition; Apply — фиксация выбранного рисунка; Cancel — возврат к предыдущему рисунку/состоянию.
- Сохранить совместимость legacy-поля `patternSlot`; миграция/переименование допустимы только с явным compatibility mapping и тестами.
- Переключение рисунка во время playback должно учитывать host sync, границы такта/события и безопасный переход без зависших нот, резких обрывов и двойного запуска.
- Музыкальная логика сохраняет уже утверждённое разделение: инструмент/источник гитары, tone preset/FX и performance articulation/pattern — независимые оси выбора.
- Недоступная в выбранной библиотеке артикуляция должна быть честно обозначена unavailable/disabled. Нельзя синтезировать отсутствующую гитарную технику и выдавать её за реальную запись.
- Сохраняются уже утверждённые PATTERN/AUTOCHORDS правила: аккордовая клавиша выбирает chord/voicing; MIDI pattern задаёт timing, gate, velocity, accent и ритм; fallback из записанных совместимых guitar one-shots допустим только внутри существующего Pattern/S6.5 pipeline и при наличии корректной карты. MELODY по-прежнему запускает отдельную ноту на клавишу.
- Display AutoChords не должен перекрывать MIDI-клавиши плагина, перехватывать их hit-testing или уменьшать доступную область клавиатуры. При нехватке места панель перестраивается/прокручивается/сворачивается либо выносится в отдельное окно.

### 6. Каталог, пользовательские данные и форматы

- Factory catalog — расширяемый, но неразрушаемый: только добавление новых записей/метаданных; запрещены удаление, замена существующих factory entries и незаметная перезапись.

## 2026-11-14 — MAJOR UI clarification: separate MELODY / PATTERN preset browsers and three-part MELODY browser

**Тип:** user-approved functional specification clarification; append-only.  
**Статус:** APPROVED / DOCUMENTATION UPDATE. Production implementation is not implied.

### A. MELODY mode — three-part browser, fixed order
The MELODY browser is divided into exactly three coordinated areas:

1. **PRESET / GUITAR IDENTITY** — choose the pop-punk guitar/genre and the relevant PUNK GROUP / band-style sound identity, then the individual song part/section. This area answers **WHICH guitar/source and which song-section character** is selected. It must follow the approved hierarchy and available source mappings; do not invent unavailable group/song mappings.
2. **STYLE / PLAYING ARTICULATION** — choose how the selected guitar performs the notes. Examples include **Open Chord, Palm Mute, Muted**, and other articulations/styles supported by the actual source maps (e.g. tremolo/picking where recorded and mapped). STYLE is not a rhythmic pattern selector. Only expose an articulation as playable when a compatible source/performance map exists.
3. **PATTERN / RHYTHM VARIATION** — choose/switch the rhythmic figure or variation associated with the selected guitar/section/style. This area is available as an optional performance layer while remaining in MELODY mode; it does not convert ordinary melody-note mapping into chord mode.

The three areas must remain visually and functionally distinct. Selection in one area must not silently overwrite the meaning/state of the other two. Compatibility filtering may limit choices to combinations supported by the selected source.

### B. MELODY note behaviour and Pattern activation
- In ordinary MELODY playing, each MIDI key plays its corresponding pitched guitar note; a single melody note plays once and naturally decays. It must not unexpectedly launch a strumming loop.
- The optional PATTERN layer activates when the user supplies the additional pattern-trigger MIDI in the Piano Roll / MIDI performance, or explicitly enables/selects the pattern using the dedicated on-screen PATTERN control/button.
- The approved Piano Roll convention reserves the lowest register **C0–C1** for pattern-trigger keys; **C1 and above** remain the ordinary melody-note register. Pattern-trigger keys must not also sound as ordinary chromatic guitar notes. Preserve the exact boundary/mapping in implementation tests and make it discoverable in the UI/help.
- Holding a valid pattern-trigger note sustains/runs the selected pattern according to its gate/transport contract; releasing it ends the pattern cleanly. A lone ordinary melody note remains a one-shot pitched note.
- The PATTERN area/button allows the user to switch between different rhythmic figures/variations. Variation changes must respect the current selection/filter context and transition safely on a musical boundary while playing; no stuck notes, duplicate triggers, timing jumps or abrupt invalid cuts.
- The on-screen control is an explicit alternate activation/selection route; it must not change the MIDI meaning of ordinary melody keys.

### C. PATTERN mode remains a separate performance mode
- MELODY and PATTERN remain distinct modes with separate note semantics and preset/performance state, while sharing the approved sample library/cache and compatible source assets.
- In PATTERN mode, mapped keys select chord/voicing and trigger the selected rhythmic guitar performance; rhythm selection is separate from PLAYING STYLE / ARTICULATION.
- PATTERN mode browser continues to select the guitar/source identity, playing style/articulation and rhythmic pattern/variation as separate dimensions. Preserve the approved PATTERN categories and eight Pattern Slots per section already recorded in the canonical requirements.
- The reference for the full playing workflow is Native Instruments Session Guitarist — Electric Sunburst Deluxe as a behavioural benchmark only; do not copy its protected code, samples, presets or UI assets.

### D. Browser/state invariants
- Keep Preview non-destructive: it auditions the candidate without changing the active preset, project, persistent DAW state or saved Pattern Slot. Apply/Select commits; Cancel restores the prior state.
- PREV/NEXT, SEARCH, FILTER, SORT and FAVORITES operate within the current result context.
- No fake controls or unsupported articulations/patterns. A missing backend/source map must be visibly unavailable/disabled with an honest reason.
- Preserve audio-thread restrictions, APVTS IDs/semantics, MIDI contracts outside the explicitly reserved pattern-trigger range, sampler ownership/lifecycle, stable preset IDs and factory/user separation.

Preserve the canonical PATTERN categories already recorded in MASTER_PRODUCT_SPEC (DOWNSTROKES, DOWN/UP, PALM MUTE, POWER CHORDS, ALTERNATE PICKING, CUSTOM PATTERNS), P1–P10 where supported by the canonical pattern catalog, and eight Pattern Slots per section. Do not invent additional pattern IDs or expose unmapped items as playable.

### PATTERN-mode behaviour
- PATTERN is a separate performance mode from MELODY. It uses rhythmic guitar performance and the approved AUTO CHORDS ON/OFF behaviour; MELODY remains one key = one pitched note.
- The PRESET window selects guitar/source identity and song context. The second window selects playing manner and rhythmic performance. Neither window silently overwrites the other window's independent selection state.
- Chord/voicing selection, guitar/source identity, tone preset/FX, playing style/articulation and rhythm pattern remain separate axes.
- Context filtering may narrow compatible choices but must not merge the two windows or conflate STYLE with PATTERN.
- Preserve non-destructive PREVIEW, explicit SELECT/APPLY and CANCEL rollback; PREV/NEXT, SEARCH, FILTER, SORT and FAVORITES retain current browser scope.
- Unsupported source/style/pattern combinations are visibly unavailable with a truthful reason; no fake controls, random substitution or incompatible sample playback.
- Both windows must respect keyboard visibility/hit-testing, realtime callback restrictions, stable IDs, existing MIDI/APVTS contracts and exact-SHA validation gates.

## MELODY — подтверждение финальной структуры и поведения (пользовательское утверждение)

**СТАТУС: УТВЕРЖДЕНО ПОЛЬЗОВАТЕЛЕМ.** Эта запись фиксирует подтверждение пользователем ранее согласованной финальной версии; не является новым проектным предложением.

### MELODY — три отдельные области
- **PRESET** — выбор гитарного пресета.
- **STYLE** — артикуляция и способ исполнения мелодии.
- **PATTERN** — ритмическая вариация внутри MELODY.
- Одна обычная MIDI-клавиша соответствует одной мелодической ноте. Обычное нажатие не должно самопроизвольно запускать strumming loop или PATTERN.

### Включение PATTERN внутри MELODY
- PATTERN внутри MELODY является дополнительной функцией.
- Для запуска используется дополнительная MIDI-прорисовка/триггер в Piano Roll.
- Зона C0–C1 выделяется для PATTERN-триггеров; выше располагается обычный мелодический диапазон. Триггерная зона не должна одновременно звучать как обычные хроматические ноты.
- Предусмотрено переключение вариаций PATTERN.
- Обычная MELODY и основной режим PATTERN остаются разными режимами.
- Без дополнительного запуска PATTERN MIDI исполняется обычно: одна нота звучит как нота, несколько одновременно заданных нот образуют соответствующий аккорд. Дополнительная MIDI-команда запускает выбранный PATTERN; основные MIDI-ноты задают исполняемую ноту или аккорд.
- PATTERN не должен самопроизвольно изменять обычное мелодическое исполнение.

### Главная структура интерфейса и расположение браузера
- Главные области интерфейса: **MELODY**, **PATTERN**, **FX EDIT**.
- Браузер располагается слева; его раскрытие и сворачивание не должно смещать основные области интерфейса.
