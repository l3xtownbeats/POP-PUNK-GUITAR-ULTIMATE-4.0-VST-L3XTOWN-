## 3. Подтверждённая техническая база и риски

Последний углублённый аудит SamplePool/SamplerEngine подтвердил:
- загрузка SFZ строит candidate snapshot и публикует его атомарно после проверки generation token;
- старые snapshots и streaming services удерживаются до уничтожения SamplePool для защиты активных raw pointers;
- текущие ограничения: до 128 snapshots и до 8 streaming library roots на экземпляр;
- SamplerEngine содержит 64 заранее выделенных voice slots;
- cache miss не должен блокировать audio thread; voice удерживает cursor до получения страницы;
- streaming worker дренирует очередь при штатной остановке;
- после исключения worker автоматически не восстанавливается.

Открытые инженерные риски:
1. безопасное освобождение старых snapshots без use-after-free;
2. совокупная память/потоки при нескольких streaming roots;
3. политика восстановления после падения streaming worker;
4. стресс 64 voices при cache pressure, queue overflow и loop prefetch;
5. cancellation/lifetime гонки при загрузке и уничтожении processor;
6. полная Windows Release + CTest + pluginval проверка после изменений.

Нельзя удалять старые snapshots простым сбросом unique_ptr, пока не доказано quiescence всех audio readers.

## 4. Архитектура семейства Guitar / Bass

Принято: один общий низкоуровневый PPGU Audio Engine и два самостоятельных продукта — Guitar Edition и Bass Edition. Общими могут стать streaming, WAV/SFZ reader, cache, queues, state/preset infrastructure, MIDI primitives, FX infrastructure и QA. Guitar/Bass артикуляции, SoundBank, presets, product identity и UI-профили остаются раздельными. Это архитектурное решение, не готовая реализация.

## 2026-11-12 — C1083 / generated BinaryData.h regression fix

**Статус:** SOURCE FIX COMMITTED; WINDOWS BUILD PENDING.  
Source commit: `0ef0ebe934350d57779328a5e0979f1134ae85f2` (parent: `e21980eee5289b00db371b3c2a907a5d0016b19a`).

В `CMakeLists.txt` добавлена отдельная JUCE binary-data цель `PPGUTestData` до создания зависимого integration-test target. Цель использует маленький нейтральный fixture `tests/assets/ppgu_test_data.txt`, namespace `PPGUTestData` и линкуется непосредственно к `ppgu_processor_pattern_tests`. Это обеспечивает generated include directory и `JUCE_TARGET_HAS_BINARY_DATA` для test target в чистом build tree.

**Важное уточнение JUCE API:** в закреплённой проектом JUCE 7.0.12 сигнатуре используется аргумент `NAMESPACE`, а не `HEADER_NAMESPACE`; сгенерированный заголовок по умолчанию называется `BinaryData.h` и попадает в include directory target. Поэтому путь `PPGUTestData/BinaryData.h` из чернового примера REV 13 не используется: JUCE добавляет generated header через `JuceHeader.h` при наличии `JUCE_TARGET_HAS_BINARY_DATA`. Основание: JUCE CMake API и реализация `juce_add_binary_data`.

GitHub Actions run #827 / ID `43113647167` создан на source commit `0ef0ebe934350d57779328a5e0979f1134ae85f2`; на момент записи состояние `queued`. Локальная Windows/MSVC Release-сборка в этой среде не выполнялась. Следовательно, исправление пока **не объявляется BUILT или TESTED**. Следующие гейты: полный build всех targets, CTest, locate VST3, pluginval strictness 5 и packaging.

Отдельное расхождение REV 13 для последующего согласования: текущий root CMake всё ещё закрепляет JUCE 7.0.12 и minimum CMake 3.22; REV 13 §13.2 требует JUCE 8 и CMake >=3.24. Версии не менялись в рамках изолированного C1083 fix, чтобы не смешивать причины сборочных регрессий.

## 6.8. SKINS: смена только визуального оформления, без изменения функций и геометрии (2026-11-12, REV.17)

Пользователь уточнил принцип на примерах FLEX и NEXUS: для пользователя переключение SKINS должно быть похоже на смену одежды/внешнего оформления. Плагин остаётся тем же инструментом; меняется визуальный стиль.

**Жёсткое разделение ответственности:**
- Базовый интерфейсный макет PPGU определяет постоянные геометрию, расположение, размеры и набор элементов управления.
- SKIN меняет только визуальное представление этих же элементов: палитру, фон, текстуры, декоративные изображения, рамки, подсветку, типографику, графику ручек/ползунков/кнопок, иконки и оформление состояний.
- SKIN не меняет layout/координаты/размеры контролов, набор функций, типы контролов, APVTS IDs, значения параметров, маршрутизацию, DSP, MIDI, пресеты, sampler, артикуляции, автоматизацию или поведение окон.
- Ручка остаётся той же ручкой с той же привязкой и диапазоном; меняется только её рисунок. Аналогично для ползунка, переключателя, дисплея, клавиатуры и каждого другого элемента.
- Смена SKIN не сбрасывает текущий пресет, значения параметров, состояние MIDI/артикуляций или настройки плагина.
- SKIN можно переключать во время работы через кнопку SKINS. Загрузка оформления выполняется на UI/message thread; аудиопоток не ждёт файловых операций и не блокируется.
- Если отдельная тема содержит собственные ассеты, они должны соответствовать фиксированным слотам/контракту базового макета. Неизвестный или отсутствующий ассет заменяется безопасным fallback без изменения геометрии и логики.
- Для будущих альтернативных оформлений допускается другая художественная стилистика, но не другая функциональная схема или расположение органов управления. Отдельная новая компоновка может появиться только как явно утверждённая новая версия базового макета, а не как обычный SKIN.

**Ориентиры UX, проверенные по официальным материалам на 2026-11-12:**
- Image-Line FLEX: отдельный выбор темы оформления в Options; единый preset browser с поиском/тегами, Play/Edit режимами и макросами.
- reFX NEXUS 5: масштабируемый интерфейс, единый заголовок с информацией о пресете, браузер категорий/папок, редакторные вкладки; N2 Retro представлен как переключаемое полностью функциональное оформление/режим.
- JUCE LookAndFeel: предназначен для изменения внешнего вида стандартных виджетов и отрисовки собственных кнопок/слайдеров без замены их функциональных компонентов.

Источники:
- Image-Line FLEX manual: https://www.image-line.com/fl-studio-learning/fl-studio-online-manual/html/plugins/FLEX.htm
- reFX NEXUS 5 manual: https://refx.com/nexus/manual
- JUCE LookAndFeel customisation: https://juce.com/tutorials/tutorial_look_and_feel_customisation/

**Реализационное следствие для PPGU:**
1. Оставить один набор JUCE-компонентов и APVTS attachments; не создавать отдельные функциональные реализации контролов для каждого SKIN.
2. Разделить SkinManifest/ThemeManager (визуальные токены и ассеты) и неизменяемый BaseLayout (bounds, порядок и идентификаторы элементов).
3. Обновление скина должно применять LookAndFeel/ресурсы к существующим компонентам и вызывать repaint/layout refresh только при необходимости; не пересоздавать processor или attachments.
4. Удалить/игнорировать skin-поля, которые пытаются менять геометрию или функциональную карту. Проверять манифест до применения; при ошибке сохранять текущую тему либо безопасный fallback.
5. Приёмочные тесты: переключить все доступные SKINS при активном пресете и ненулевых параметрах; проверить неизменность APVTS values, control IDs, component bounds, MIDI, звука и открытых панелей. Проверить повторное открытие проекта и восстановление выбранного SKIN.

**Текущее состояние аудита:** PluginEditor уже имеет кнопку SKIN, popup-выбор темы и применение палитры через ThemeManager/LookAndFeel. Однако подтверждённого полного набора сменных графических ассетов и теста неизменности геометрии/состояния между SKINS пока нет. Также обнаружено расхождение схем: SKIN/Skin_01/theme.json использует старую структуру tokens/assets, тогда как ThemeManager содержит отдельный валидатор Skin Studio schemaVersion 1.0.0 с обязательными palette/controls/compatibility. До унификации схем нельзя считать все темы взаимозаменяемыми и готовыми к runtime hot-swap.

**Статус:** REQUIREMENT ACCEPTED; CURRENT CODE PARTIAL; FULL SKIN HOT-SWAP TEST PENDING; HOST VERIFIED NO.


## 6.10. UX: запуск сразу в утверждённой оболочке и простая смена SKINS (2026-11-12)

Пользователь утвердил обязательный сценарий использования:
- При первом открытии VST3 сразу отображается утверждённая базовая оболочка PPGU (Main Window), без промежуточного экрана, выбора темы или ручной настройки.
- Базовый утверждённый скин назначен темой по умолчанию. Если сохранён другой выбранный скин, при последующем запуске восстанавливается именно он.
- Для смены оформления пользователь нажимает одну кнопку SKINS, видит понятный список доступных тем с названиями и, где доступно, миниатюрами/превью.
- Один выбор применяет тему сразу к интерфейсу; не требуется перезапуск плагина, закрытие проекта или повторная загрузка инструмента.

- В обычном сценарии интерфейс должен быть очевиден без инструкции: Main Window при старте, SKINS для внешнего вида, X для закрытия внутренних панелей.

**Инженерные критерии:**
1. Базовый layout и control map неизменны для всех скинов; тема не может менять bounds, порядок или APVTS bindings.
2. Выбранная тема сохраняется в настройках UI; восстановление выполняется при создании Editor до первого отображения.
3. При отсутствующей/повреждённой теме автоматически загружается утверждённая базовая тема, без блокировки запуска.
4. Применение темы выполняется только на JUCE message thread; никаких файловых операций или ожидания в аудиопотоке.
5. Hot-swap не пересоздаёт AudioProcessor, attachments, sampler или DSP и не сбрасывает параметрические значения.
6. Приёмка: открыть VST3 в FL Studio 20 → сразу увидеть утверждённый Main Window → изменить несколько параметров и включить FX → выбрать другой SKIN → убедиться, что внешний вид изменился, а bounds, параметры, пресет и звук сохранились → закрыть/открыть проект и проверить восстановление выбранного скина.

**Состояние кода по текущему аудиту REV.17:** базовый редактор уже создаётся сразу и содержит кнопку SKIN, popup выбора и сохранение выбора через UI Properties. Однако утверждённый макет ещё не перенесён один к одному; текущий paint/resized строит отдельную компоновку. Поэтому UX-требование принято, но реализация пока частичная. Не объявлять задачу завершённой до точного переноса макета, проверки переключения тем и запуска VST3 в хосте.
