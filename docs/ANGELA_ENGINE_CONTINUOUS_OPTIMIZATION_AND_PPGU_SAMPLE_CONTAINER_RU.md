# ANGELA Engine — непрерывная оптимизация и собственный формат библиотек

Дата утверждения: 14 ноября 2026  
Статус: обязательное архитектурное правило / проектирование; реализация поэтапная, без переписывания движка с нуля.

## 1. Утверждённое правило развития ANGELA Engine

ANGELA Engine необходимо постоянно улучшать, модернизировать и оптимизировать для минимального практического потребления CPU, RAM, дискового пространства и времени запуска/загрузки. Развитие ведётся **эволюционно, поверх существующей архитектуры**, без полной пересборки с нуля и без необоснованной замены работающих компонентов.

Обязательные ограничения:
- сохранять существующие функции, пользовательские сценарии, MIDI/артикуляции, пресеты, маршрутизацию и звучание;
- до каждого изменения изучать затрагиваемый код, контракты и тесты;
- делать небольшие изолированные изменения с измеримым результатом;
- сохранять обратную совместимость форматов и пресетов либо предоставлять безопасную миграцию;
- иметь regression tests и A/B проверки звучания до/после;
- не принимать оптимизацию, если она ухудшает звук, стабильность, совместимость или функциональность;
- измерять CPU, RAM, startup, preset-load, disk I/O, cache hit/miss, underruns на одинаковых сценариях и оборудовании;
- не заявлять «быстрее/легче», пока это не подтверждено benchmark;
- никакой файловой операции, декодирования, ожидания, блокировки, непредсказуемого выделения/освобождения памяти в realtime audio callback;
- оптимизации внедрять поэтапно, с возможностью отката, не ломая существующий ANGELA Engine.

## 2. Исходные библиотеки и сохранность оригиналов

Загруженные исходные библиотеки остаются на исходных ресурсах/носителях, где они хранятся. Конвертация в формат PPGU создаёт **дополнительную производную копию** и никогда не удаляет, не перемещает, не переименовывает и не перезаписывает оригиналы.

- Сохранять source URI/path, имя, исходный формат, размер, даты/метаданные (если доступны), SHA-256, источник и лицензионное доказательство.
- Не считать лицензию «royalty-free» автоматическим разрешением на включение/распространение производных библиотек.
- Конвертировать/паковать можно только после проверки, что лицензия разрешает преобразование и включение производного контента в коммерческий VST-плагин.
- Если лицензия неясна или запрещает распространение/производные работы, источник остаётся только внешним/неинтегрированным до получения разрешения.
- Конвертация не должна менять музыкальную разметку: key/velocity ranges, root key, round-robin, articulation, loop/start/end, tuning, gain/pan и происхождение семпла.

## 3. Целевой собственный формат PPGU

Рабочее имя: **PPGU Sample Container (PSC)**; предлагаемое расширение: `.ppgs`. Это спецификация для проектирования, не заявление о готовой реализации.

Цели:
- быстрый индекс и доступ к отдельным семплам/страницам без распаковки всей библиотеки;
- меньше занимаемое место при сохранении исходного качества;
- детерминированный random access и потоковое чтение;
- целостность и проверяемое происхождение;
- безопасная миграция и совместимость будущих версий.

Предлагаемая структура контейнера:
1. Fixed header: magic, format version, endian marker, flags, index offset/length, content UUID, manifest hash.
2. Manifest/index: список samples и source provenance; codec, channels, sample rate, frame count, bit depth, loop markers, articulation, velocity/key zones, round-robin, tuning и контрольные суммы.
3. Chunk table: независимые временные аудиоблоки фиксированного/адаптивного размера с frame offset, byte offset, encoded length, decoded length, codec, CRC32C и/или SHA-256.
4. Payload: аудиоблоки, допускающие чтение конкретного блока без полной распаковки контейнера.
5. Optional embedded SFZ/PPGU mapping metadata and license/provenance records.

### Кодек и качество
- Для мастер-архива/конвертации по умолчанию сначала оценивать lossless-кодирование (например FLAC в независимых чанках) против PCM; сравнивать размер, скорость random seek/decode и CPU на Windows 10 x64.
- Не применять lossy-кодирование к factory guitar source samples без отдельного явного решения и слепого аудио-QA.
- Хранить исходный sample rate и каналы; не делать обязательный downsample/resample. Дополнительные производные версии допускаются только как отдельные профили с сохранением исходного lossless-источника.
- Если FLAC decode создаёт лишнюю нагрузку или ухудшает cache-miss behavior, PCM chunk payload остаётся безопасным fallback. «Свой формат» — это контейнер, индекс, метаданные, checksums и потоковая организация; он не обязан изобретать новый аудиокодек.

## 4. Загрузка и воспроизведение

- Converter/importer работает только в background worker / offline tool.
- Runtime открывает контейнер, читает индекс, затем запрашивает необходимые чанки через bounded request queue.
- Audio thread получает только готовые опубликованные страницы через существующий non-blocking cache/lease protocol.
- Cache miss не блокирует audio thread; фиксируется underrun/diagnostic counter и применяется существующее безопасное поведение.
- Кэш ограничен явным RAM budget, освобождение страниц и snapshot lifetime выполняются вне audio thread.
- Presets хранят стабильные library/sample IDs и относительные ссылки, не абсолютные временные пути и не дублируют payload.
- Сохранить SFZ/WAV как поддерживаемые исходные/совместимые форматы; PSC вводить дополнительно, не ломая их загрузку.

## 5. Миграция и проверка

1. Сканировать библиотеку, получить manifest и SHA-256.
2. Проверить лицензию и разрешение на производную копию.
3. Конвертировать в уникальный новый путь; не менять оригинал.
4. Сверить число samples, длительность, sample rate, channels, loops, mappings, velocity/articulation layers.
5. Для lossless профиля сравнить decoded PCM sample-for-sample либо по строгому цифровому критерию.
6. Прогнать SFZ/preset regression, note/loop/round-robin/articulation tests, cache stress, corruption/truncation tests.
7. A/B сравнить звучание, CPU, RAM, disk I/O, cold/warm load и seek latency.
8. Только после QA отметить PSC-версию как validated; оригиналы оставить доступными для rollback.
9. При сбое/повреждении контейнера безопасно вернуться к исходному WAV/SFZ, не удаляя PSC и не повреждая библиотеку.

## 6. Единый лимит библиотеки

Утверждённый жёсткий потолок управляемой папки `Samples`: **40 GB decimal = 40,000,000,000 bytes**.

- Прежний 25 GB per-run лимит Sound Hunter полностью снят; нового лимита на один запуск нет.
- Ограничивается только суммарный физический размер поддерживаемых аудиоактивов/контейнеров, размещённых внутри managed `Samples`; приёмка каждого нового файла/контейнера должна проверять, что общий размер после добавления не превысит 40,000,000,000 bytes.
- Конвертированные PSC-файлы внутри `Samples` учитываются по фактическому размеру на диске.
- Внешние оригиналы на исходных ресурсах вне `Samples`, которые плагин использует без копирования, не удаляются и не учитываются в размере этой папки.
- Если для работы нужна локальная копия исходника внутри `Samples`, она учитывается; при конвертации нельзя автоматически оставлять и исходную копию, и PSC, если это превышает потолок. Однако оригинал на внешнем исходном ресурсе сохраняется.
- Дубликаты не должны повторно занимать место: идентификация по криптографическому хэшу с проверкой содержимого.
- При нехватке места — отказ/предупреждение до записи, никаких автоматических удалений/перезаписей.
- 40 GB — максимум, а не цель заполнения; качество, лицензия и реальная полезность важнее объёма.

## 7. Текущее состояние / запрет ложных заявлений

В репозитории уже существуют SFZ parser, WAV metadata index, background WAV page streaming, bounded request queue, fixed-size page cache и per-voice page reader. Их следует развивать и защищать от регрессий. При этом отдельные файлы/компоненты старого корневого prototype могут быть заглушками; наличие класса или заголовка само по себе не доказывает production readiness.

На момент фиксации этого правила:
- PSC container format не реализован и не интегрирован;
- converter/migrator не реализован;
- сравнительные benchmark PSC vs WAV/FLAC/PCM не выполнялись;
- нельзя заявлять, что библиотека уже конвертируется, занимает меньше места или загружается быстрее;
- дальнейшая работа начинается с аудита действующего production path и небольшого прототипа контейнера/читателя с regression tests.

## 8. Приоритеты следующей реализации

A. Зафиксировать baseline benchmark существующего ANGELA streaming path (CPU, RAM, cold/warm load, page cache, underrun).  
B. Проверить реальные точки входа production SamplerEngine/SamplePool и защитить их тестами.  
C. Спроектировать PSC v1 binary layout и parser/validator, включая versioning, bounds checks, checksums и fuzz/corruption tests.  
D. Реализовать offline converter, который создаёт новый файл и не трогает source.  
E. Добавить PSC page reader как новый source backend рядом с WAV reader; не заменять WAV path до A/B и regression pass.  
F. Включить общий 40 GB capacity guard в Sound Hunter, ручной импорт и конвертер до записи.  
G. Выполнить Windows 10 x64 Release build, CTest, pluginval и тесты в FL Studio 20.
