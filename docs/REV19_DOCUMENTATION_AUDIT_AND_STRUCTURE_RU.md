## 3. Карта продукта — логическая последовательность

### A. Основа продукта и управление
- Идентичность продукта, платформа, VST3, Windows x64, целевой хост FL Studio 20.
- Архитектурные инварианты: realtime safety, отсутствие блокирующей работы в audio callback, стабильное состояние, ограниченные ресурсы.
- Каноническая ветка, контроль изменений, журнал, решения, статусы, доказательства.

### B. Интерфейс и визуальная система
1. SIGNAL FORGE / CONTROL DECK — единственный функциональный источник истины.
2. 27 утверждённых пользовательских контролов и существующие ID/назначения.
3. Семь утверждённых FX bypass IDs.
4. NEON STAGE — эталонный GRAPHIC SKIN, визуально отражающий утверждённый CONTROL DECK.
5. Остальные 15 тем — только оформление того же функционального набора.
6. Галерея тем — список только 16 утверждённых заводских тем, выбор, состояния и безопасное применение.
7. Состояния контролов, доступность, фокус, масштабирование, читаемость и сохранение выбора.
8. Ни один макет не считается runtime-реализацией без проверки.

### C. Музыкальные режимы
- MELODY: клавиша MIDI запускает отдельную ноту/исполнение соответствующего инструмента.
- PATTERN: клавиша выбирает аккорд и запускает утверждённое ритмическое исполнение; разделы/паттерны/переходы описываются отдельными контрактами.
- PUNK GROUP и AUTOCHORDS — только в объёме, подтверждённом актуальными утверждениями и фактической реализацией; их маршрутизация и зависимость от MELODY/PATTERN проверяются отдельно.
- MELODY и PATTERN используют общий sampler/core, если это подтверждено текущей архитектурой; не создавать параллельные дублирующие движки.

### D. Звуковой тракт и движок
1. MIDI input, mapping, articulation и voice lifecycle.
2. Sampler: WAV/SFZ, mapping, velocity/key/channel, round-robin, streaming/cache.
3. MELODY/PATTERN orchestration и связь с общим sampler.
4. Audio signal flow, gain staging, preset level, dry/wet, routing, output protection.
5. FX/DSP и их реальное подключение к аудиотракту и UI.
6. Click-free transitions, latency, recovery, error handling, state/preset persistence.
7. Качество и согласованность звучания — отдельная проверка, не вывод из наличия DSP-классов.

### E. Контент и библиотека
- Factory presets: определения, доступность ресурсов, runtime mapping, playable QA.
- Sample Library / Import Sample Guitar / runtime SOUNDBANK — разные назначения и пути, если это предусмотрено утверждённым portable layout.
- Sound Hunter / лицензии / provenance / SHA-256 / legal review / технический и человеческий аудиоконтроль.

- Каталог пресетов не равен числу реально готовых и прослушанных пресетов.

## 4. Первичный аудит структуры репозитория

На проверенном дереве REV.19 обнаружены следующие документальные узлы:

- `PPGU_JOURNAL.txt` — отдельный крупный исторический журнал/накопитель решений; конкурирует с правилом единственного INFO и требует извлечения только актуальных утверждений, затем перевода в архивный статус.
- `PPGU_TASK_REGISTRY.md` — содержит секции REV.18 и старые статусы/приоритеты наряду с REV.19. Нельзя использовать как чистый актуальный реестр до сверки.
- `PPGU_WINDOWS_PANELS_INVENTORY.md` — полезный начальный список, но в нём смешаны SOURCE PRESENT, DESIGNED, PARTIAL и NOT IMPLEMENTED; перечень необходимо дополнить по актуальным макетам и коду.
- `docs/PPGU_MASTER_IMPLEMENTATION_REGISTER_RU.md` — содержательный сводный документ, но включает исторические REV.17/18 checkpoints, старые числа тем и прежние очереди. Требует переписывания в чистую REV.19 структуру с отдельной историей.
- `docs/PPGU_DEVELOPMENT_CONTROL_CENTER.md` и `docs/PPGU_MASTER_PROMPT_RU.md` — содержат полезные правила, но в заголовках/тексте ссылаются на прежние канонические ветки REV.17 и старую иерархию. Требуется сверка и маркировка как исторических/частично применимых, а не безусловно действующих.
- Несколько UI/theme спецификаций помечены REV.17/REV.18 и существуют в нескольких копиях/вариантах. Их нельзя считать параллельными текущими спецификациями.
- `README_JOURNAL_CONTINUATION.md` — пакет инструкций по продолжению старых журналов; после консолидации не должен использоваться как отдельный источник актуальных требований.
- `SKIN/theme_manifest.json` и legacy каталоги Skin_01…Skin_102 присутствуют в дереве, хотя действующая продуктовая база допускает только 16 тем. Это документально-ресурсное несоответствие, которое надо устранить в согласованном порядке; не восстанавливать 102 темы и не использовать их как часть продукта.
- SKIN-103…SKIN-117 имеют JSON и SVG-ресурсы в дереве, но наличие файлов само по себе не доказывает полноту ассетов, паритет или runtime-готовность.
- UI inventory и документы по дополнительным окнам не являются полным source-to-control audit.

**Важно:** это первичный структурный аудит выбранных ключевых файлов и дерева репозитория. Он не означает, что каждая из 958 файлов проверена по содержимому или что все исторические требования уже разрешены.

## 5. Что считать активным, историческим и исключённым

| Класс | Правило |
|---|---|
| ACTIVE / APPROVED | Последнее утверждённое требование, применимое к REV.19 |
| ACTIVE / IMPLEMENTED | Реализация найдена в текущем коде; проверка указывается отдельно |
| ACTIVE / BLOCKED | Утверждённое требование с конкретным блокером |
| PROPOSED | Идея без утверждения; не включать в обязательную разработку |
| SUPERSEDED | Заменено более поздним решением; не использовать |
| HISTORICAL | История/аудит прежних веток; только справочно |
| EXCLUDED | Прямо исключено пользователем из проекта |
| UNVERIFIED | Недостаточно данных для точного статуса; не додумывать |

## 7. Правило оформления каждой записи

- уникальный ID;
- название и короткое русское пояснение;
- область/родительский раздел;
