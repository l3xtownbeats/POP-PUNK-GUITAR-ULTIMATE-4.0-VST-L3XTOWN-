# PPGU — единая функциональная архитектура 16 визуальных тем

Статус: утверждённый архитектурный контракт; реализация и приёмочные тесты выполняются отдельно.

## Решение

Все 16 тем используют одну функциональную архитектуру редактора. Тема не является отдельной раскладкой и не может менять назначение, идентификатор, доступность или порядок основных элементов управления. Визуальная индивидуальность создаётся с помощью материалов, графики и скинов контролов.

Исключение допускается только для декоративной геометрии: внутренние отступы, рамки, радиусы, текстуры, световые эффекты и декоративные слои могут различаться, если это не меняет фактическую область взаимодействия, порядок фокуса и расположение функциональных блоков.

## Неизменяемый слой (Functional Layout Contract)

Для всех тем общими остаются:

- дерево функциональных компонентов и их стабильные component IDs;
- координатная схема и anchors основных функциональных блоков;
- назначение, порядок и доступность контролов;
- размеры hit-targets и правила доступности;
- привязки к APVTS parameter IDs;
- MIDI mappings, preset/state handling и processor state;
- открытие, закрытие, перемещение и восстановление дополнительных окон;
- поведение при resize и DPI scaling.

Тема не может добавлять фиктивные контролы, скрывать обязательные контролы, переназначать параметры, менять порядок tab/focus navigation или создавать альтернативный layout.

## Разрешённый визуальный слой (Theme Skin Contract)

Каждая тема может иметь собственные:

- поверхности, материалы, текстуры, рамки, градиенты и тени;
- artwork, фоны, логотипы и декоративные изображения;
- форму/материал/обводку регуляторов при сохранении одинакового взаимодействия;
- оформление кнопок, переключателей, combo boxes и индикаторов;
- оформление LCD, LED, виртуальной клавиатуры и FX-блоков;
- оформление главного окна и всех вспомогательных окон;
- hover, pressed, focused, disabled и selected states;
- анимацию переходов, если она не мешает ECO/reduced-motion режиму.

Каждая тема должна иметь полноценный комплект состояний для каждого поддерживаемого типа контрола. Отсутствующие ресурсы должны приводить к безопасному fallback стилю, а не к невидимым/неработающим контролам.

## Модель данных темы

Theme manifest описывает только визуальные свойства и ресурсы. Рекомендуемые группы:

1. `identity`: stable theme ID, display name, family, schema version.
2. `palette`: canonical 21-token palette.
3. `materials`: фоновые поверхности, текстуры, bevel, metal/wood/carbon treatments.
4. `controls`: визуальные стили по стабильному типу компонента, без новых параметрических связей.
5. `artwork`: preview, hero, logo/crest и декоративные assets.
6. `states`: normal, hover, pressed, focused, disabled, selected.
7. `compatibility`: visualOnly=true, layoutChanges=false, apvtsChanges=false, audioChanges=false.

Manifest не должен задавать произвольные координаты функциональных контролов. Любые legacy layout fields трактуются как неисполняемые метаданные до отдельного утверждения и тестирования.

## Инварианты переключения

Preview:
- временно показывает визуальную тему;
- не меняет сохранённый выбор;
- при отмене возвращает последнюю применённую тему.

Apply:
- сначала валидирует ID, manifest и обязательные ресурсы;
- применяет тему только после успешной проверки;
- сохраняет stable ID только после успешного применения.

При старте:
- новый профиль получает утверждённую REV 7 NEON;
- существующий профиль восстанавливает последнюю вручную применённую валидную тему;
- неизвестный/повреждённый ID безопасно возвращается к NEON;
- fallback не должен менять звук, состояние процессора или прерывать аудио.

## NEON — исключение по статусу, не по архитектуре

«Неоновый интерфейс PPGU для поп-панк гитары» из REV 7 — неизменяемый визуальный эталон и тема первого запуска. Запрещено перестраивать её ради унификации с альтернативными темами. Общая архитектура подстраивается под утверждённый NEON layout, а не наоборот.

REV 7 assets должны быть восстановлены и идентифицированы по точной ветке/коммиту и blob SHA до фиксации NEON palette/artwork или изменения runtime default. Нельзя подменять эталон темой Neon Riot, Neon Flagship, Blackout Voltage, Carbon Relay или другим похожим названием.

## Приёмочные проверки

- Сравнить component IDs, control inventory и functional bounds для всех 16 тем.
- Проверить отсутствие layout mutations при Preview/Apply.
- Сверить APVTS IDs/values, preset/state, MIDI и processor state до и после переключения.
- Проверить, что переключение темы не меняет rendered audio.
- Проверить все control states и вспомогательные окна в каждой теме.
- Проверить resize и DPI 100/125/150%, keyboard focus и hit-targets.
- Проверить повреждённые manifests/assets, fallback, отмену Preview и persistence Apply.
- Не считать тему готовой по одной палитре: необходимы визуальные ресурсы и проверка всех реальных компонентов.

## Текущий блокер

На момент фиксации в ветке `work/neon-gallery-16-skins` runtime ThemeManager по умолчанию использует `skin-51 / Blackout Voltage`, а registry указывает `defaultSkin: skin-51`. Поиск веток по `REV 7` и `rev7`, а также поиск по точному названию макета не вернули подтверждённый источник. Поэтому менять runtime default или объявлять NEON восстановленным до идентификации трёх REV 7 файлов небезопасно.
